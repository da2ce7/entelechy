## 1. Scope & Constraints

### In scope

- Extending `src/backends/opencl/type_mapping.py` with FP8 dtype → OpenCL type mappings.
- Including the generated FP8→FP32 conversion lookup tables in `kernels.cl.h` (generated by Phase 9A.1.5).
- Implementing `load_storage_fp8()` and `store_storage_fp8()` inline functions in `kernels.cl.h` with both FP32 and FP16 compute type variants.
- Extending the precision boundary macros to dispatch to FP8 functions when `STORAGE_TYPE_IS_FP8 == 1`, with appropriate widening to `COMPUTE_TYPE` (half or float).
- Adding build flag emission for `STORAGE_TYPE_IS_FP8`, `STORAGE_TYPE_IS_E4M3`, `STORAGE_TYPE_IS_E5M2`.
- Adding OpenCL-specific FP8 roundtrip tests.

### Out of scope

- Native FP8 extension support (`CL_FP8_NATIVE`) — no such extension exists; software emulation is the only path.
- SIMD FP8 operations — FP8 is processed element-by-element via lookup tables.
- CPU backend changes — deferred to Phase 9C.
- Vulkan backend changes — deferred to Phase 9D.
- Host-side scaling logic — deferred to Phase 9E.

### Key constraint: FP8 as `uchar`

OpenCL has no native FP8 type. FP8 storage buffers are declared as `__global const uchar*` or `__global uchar*`. All arithmetic is performed in `COMPUTE_TYPE` — either `half` (FP16) or `float` (FP32), depending on the precision configuration. Conversion functions handle the FP8↔COMPUTE_TYPE boundary.

**Future native FP8 support:** Some vendors may expose FP8 via OpenCL extensions (e.g., a hypothetical `cl_nv_fp8`). This implementation does not probe for such extensions — software emulation via lookup tables is the baseline. If native FP8 support becomes available, the conversion functions in `kernels.cl.h` can be conditionally compiled to use intrinsics while maintaining the same function signatures.

### Step 9B.3: Implement FP8 `load_storage` / `store_storage`

**Governing authority:** ADR-025 §4, §6.2  
**File:** `kernels/kernels.cl.h`

Add inline conversion functions supporting both FP32 and FP16 compute:

> **`idx` type note:** The existing `load_storage` / `store_storage` functions in
> `kernels.cl.h` use `int idx`. The FP8 helpers below use `size_t idx` for
> consistency with `buf[idx]` (pointer arithmetic on `__global uchar*`). When
> wiring the FP8 helpers into the existing dispatch (Step 9B.3 bottom), the
> `int idx` from the caller is implicitly promoted to `size_t` — this is safe
> for all realistic buffer sizes, but **verify** the existing `load_storage`
> signature. If it uses `int`, consider widening it to `size_t` across all
> branches (FP8 and non-FP8) in a single pass to avoid mixed-sign comparison
> warnings (`-Wsign-compare`).

```c
#if STORAGE_TYPE_IS_FP8

// --- FP8 Load (storage → compute) ---
// Returns COMPUTE_TYPE (half, float, or double)
// Note: LUT stores float values. FP8→float is lossless (all 256 FP8 values
// are exactly representable in float). FP16 compute narrows; FP64 widens.
static inline COMPUTE_TYPE load_storage_fp8(__global const uchar *buf, size_t idx) {
#if STORAGE_TYPE_IS_E4M3
    float f32_val = fp8_e4m3_to_float_lut[buf[idx]];
#elif STORAGE_TYPE_IS_E5M2
    float f32_val = fp8_e5m2_to_float_lut[buf[idx]];
#endif

#if COMPUTE_TYPE_IS_HALF
    return (half)f32_val;    // Narrow to FP16 compute
#elif COMPUTE_TYPE_IS_DOUBLE
    return (double)f32_val;  // Widen to FP64 compute (lossless)
#else
    return f32_val;          // FP32 compute
#endif
}

// --- FP8 Store (compute → storage) ---
// Accepts COMPUTE_TYPE (half, float, or double), converts to FP8
//
// NaN handling:
//   E4M3 (float8_e4m3fn) has no NaN representation — all 256 bit patterns
//   are finite values. E5M2, by contrast, DOES have IEEE-like inf/NaN
//   (exponent 0x1F), but the store path never writes those bit patterns —
//   it saturates to the maximum finite value (0x7B / 0xFB) instead.
//
// For BOTH formats, NaN input maps to zero:
// 1. NaN in gradients indicates upstream numerical instability that should be
//    caught before reaching FP8 conversion.
// 2. Zero gradients produce no parameter update ("safe" failure mode), whereas
//    max-value gradients could cause divergence.
// 3. This matches ml_dtypes.float8_e4m3fn behavior and the CPU backend (cpu_fp8.h).
//
// If fail-fast NaN propagation is desired, check for NaN in host code before
// invoking OpenCL kernels.
static inline void store_storage_fp8(__global uchar *buf, size_t idx, COMPUTE_TYPE val) {
#if COMPUTE_TYPE_IS_DOUBLE
    // NaN check BEFORE clamp: fmin/fmax(NaN, x) == x per IEEE 754 minNum/maxNum,
    // so NaN would be silently converted to ±FLT_MAX by the clamp below.
    double dval = (double)val;
    if (isnan(dval)) {
        buf[idx] = 0x00;
        return;
    }
    // Defense-in-depth: clamp before double→float narrowing to prevent UB
    // (C99 §6.3.1.5: double→float overflow is undefined behavior).
    // Pre-scaling (Phase 9E) ensures values are in FP8 range ⊂ FP32 range,
    // so this clamp is redundant under correct operation. See "Note on FP64
    // precision" below.
    dval = fmin(fmax(dval, -(double)FLT_MAX), (double)FLT_MAX);
    float fval = (float)dval;
#else
    // Narrow to float for bit manipulation (FP8 fits in float exactly)
    float fval = (float)val;
    // NaN → zero (see rationale above)
    if (isnan(fval)) {
        buf[idx] = 0x00;
        return;
    }
#endif
    
    // Handle sign
    uint sign = (fval < 0.0f) ? 1 : 0;
    fval = fabs(fval);
    
#if STORAGE_TYPE_IS_E4M3
    // E4M3: bias=7, max=448, min_subnormal=2^-9
    const float MAX_VAL = 448.0f;
    const float MIN_SUBNORMAL = 0.001953125f;  // 2^-9
    
    // Saturation: >= is intentional. 0x7E encodes exactly 448.0, so fval == MAX_VAL
    // short-circuits to the same result the rounding path would produce. This avoids
    // unnecessary bit manipulation for a value we already know the answer to.
    if (fval >= MAX_VAL) {
        buf[idx] = sign ? 0xFE : 0x7E;  // Max magnitude (saturation, no inf)
        return;
    }
    if (fval < MIN_SUBNORMAL * 0.5f) {
        buf[idx] = sign ? 0x80 : 0x00;  // Zero
        return;
    }
    
    // Extract FP32 exponent and mantissa via bit cast
    uint fbits = as_uint(fval);
    int exp32 = ((fbits >> 23) & 0xFF) - 127;  // Unbiased exponent
    uint mant32 = fbits & 0x7FFFFF;            // 23-bit mantissa
    
    // Compute FP8 exponent
    int exp8 = exp32 + 7;  // E4M3 bias = 7
    
    // Handle subnormals
    if (exp8 <= 0) {
        int shift = 1 - exp8;
        if (shift >= 24) {
            buf[idx] = sign ? 0x80 : 0x00;  // Underflow to zero (shift >= 24 is UB)
            return;
        }
        mant32 = (mant32 | 0x800000) >> shift;
        exp8 = 0;
    } else if (exp8 >= 15) {
        buf[idx] = sign ? 0xFE : 0x7E;
        return;
    }
    
    // Round mantissa to 3 bits (round-to-nearest-even)
    uint round_bit = (mant32 >> 19) & 1u;
    uint sticky = mant32 & ((1u << 19) - 1u);
    uint mant8 = mant32 >> 20;
    if (round_bit && (sticky || (mant8 & 1u))) {
        mant8++;
    }
    if (mant8 >= 8) {
        mant8 = 0;
        exp8++;
        if (exp8 >= 15) {
            buf[idx] = sign ? 0xFE : 0x7E;
            return;
        }
    }
    
    buf[idx] = (sign << 7) | (exp8 << 3) | (mant8 & 0x7);
    
#elif STORAGE_TYPE_IS_E5M2
    // E5M2: bias=15, max=57344, min_subnormal=2^-16
    const float MAX_VAL = 57344.0f;
    const float MIN_SUBNORMAL = 0.0000152587890625f;  // 2^-16, exact
    
    // Saturation: >= is intentional. 0x7B encodes exactly 57344.0, so fval == MAX_VAL
    // short-circuits to the same result the rounding path would produce.
    if (fval >= MAX_VAL) {
        buf[idx] = sign ? 0xFB : 0x7B;  // Max magnitude
        return;
    }
    if (fval < MIN_SUBNORMAL * 0.5f) {
        buf[idx] = sign ? 0x80 : 0x00;  // Zero
        return;
    }
    
    // Extract FP32 exponent and mantissa via bit cast
    uint fbits = as_uint(fval);
    int exp32 = ((fbits >> 23) & 0xFF) - 127;
    uint mant32 = fbits & 0x7FFFFF;
    
    // Compute FP8 exponent
    int exp8 = exp32 + 15;  // E5M2 bias = 15
    
    // Handle subnormals
    if (exp8 <= 0) {
        int shift = 1 - exp8;
        if (shift >= 24) {
            buf[idx] = sign ? 0x80 : 0x00;  // Underflow to zero (shift >= 24 is UB)
            return;
        }
        mant32 = (mant32 | 0x800000) >> shift;
        exp8 = 0;
    } else if (exp8 >= 31) {
        buf[idx] = sign ? 0xFB : 0x7B;
        return;
    }
    
    // Round mantissa to 2 bits (round-to-nearest-even)
    uint round_bit = (mant32 >> 20) & 1u;
    uint sticky = mant32 & ((1u << 20) - 1u);
    uint mant8 = mant32 >> 21;
    if (round_bit && (sticky || (mant8 & 1u))) {
        mant8++;
    }
    if (mant8 >= 4) {
        mant8 = 0;
        exp8++;
        if (exp8 >= 31) {
            buf[idx] = sign ? 0xFB : 0x7B;
            return;
        }
    }
    
    buf[idx] = (sign << 7) | (exp8 << 2) | (mant8 & 0x3);
    
#endif
}

// --- Extend existing load_storage / store_storage inline functions ---
// **Resolved:** The existing load_storage/store_storage in kernels.cl.h are
// inline functions (NOT #define macros) — verified at kernels.cl.h lines 123–140.
// The #undef/#define approach would be ill-formed. Instead, add #elif branches
// to the EXISTING inline function bodies in kernels.cl.h.
//
// **Implementation:** Modify the existing inline functions (do NOT add new
// definitions here) by inserting #elif STORAGE_TYPE_IS_FP8 branches:
//
//   inline COMPUTE_TYPE load_storage(__global const STORAGE_TYPE* buf, int idx) {
//       #if STORAGE_TYPE_IS_HALF
//           return convert_compute(buf[idx]);
//       #elif STORAGE_TYPE_IS_FP8
//           return load_storage_fp8((__global const uchar*)(buf), idx);
//       #else
//           return (COMPUTE_TYPE)buf[idx];
//       #endif
//   }
//
//   inline void store_storage(__global STORAGE_TYPE* buf, int idx, COMPUTE_TYPE val) {
//       #if STORAGE_TYPE_IS_HALF
//           buf[idx] = convert_from_compute(val);
//       #elif STORAGE_TYPE_IS_FP8
//           store_storage_fp8((__global uchar*)(buf), idx, val);
//       #else
//           buf[idx] = (STORAGE_TYPE)val;
//       #endif
//   }
//
// When STORAGE_TYPE_IS_FP8 == 1, STORAGE_TYPE is defined as uchar by the build
// flags (Step 9B.4), so the __global const STORAGE_TYPE* parameter is already
// __global const uchar* — the cast is for documentation clarity.

#endif // STORAGE_TYPE_IS_FP8

// Note: When STORAGE_TYPE_IS_FP8 == 0, the existing load_storage/store_storage
// inline functions retain their original FP16/FP32/FP64 dispatch (the #elif
// branches are compiled out). The FP8 helpers above only participate when FP8
// storage is configured via build flags.
```

**Note on FP64 precision:** When storing FP64 compute results to FP8, values are first narrowed to float (which may lose precision for values outside float's range), then quantized to FP8. This is acceptable because:
1. FP8's range (max 448 or 57344) is well within float's range (~3.4e38)
2. Values destined for FP8 storage should already be scaled to fit by the host
3. FP64 values > float max would already exceed FP8's range and saturate anyway
4. The narrowing step is exact for all values ≤ FP8 max (since FP8 ⊂ FP32 ⊂ FP64)

> **FP64 narrowing is safe because values are pre-scaled.** The host-side FP8 scaling path
> (Phase 9E) ensures all values are within `storage_fp_format_max` (448 or 57344) before
> kernel invocation. Since both FP8 max values are well within float's range (~3.4e38),
> the intermediate `(float)val` cast is exact for all values that survive the scaling step.
> The `#if COMPUTE_TYPE_IS_DOUBLE` defense-in-depth clamp in the code above prevents UB
> unconditionally, even if upstream scaling is bypassed or buggy.

The key insight: FP8↔FP16 conversion routes through FP32 intermediate since all FP8 values are exactly representable in FP32.

```python
import numpy as np
from shared.precision_config import PrecisionConfig, FP8_E4M3, FP8_E5M2, FP8_DTYPES
from typing import List

def _emit_precision_flags(self, precision: PrecisionConfig) -> List[str]:
    flags = []
    
    # ... existing storage/compute/state type flags ...
    
    # FP8 storage flags (ADR-025 §3)
    is_fp8 = precision.storage_dtype in FP8_DTYPES
    flags.append(f"-DSTORAGE_TYPE_IS_FP8={1 if is_fp8 else 0}")
    flags.append(f"-DSTORAGE_TYPE_IS_E4M3={1 if precision.storage_dtype == FP8_E4M3 else 0}")
    flags.append(f"-DSTORAGE_TYPE_IS_E5M2={1 if precision.storage_dtype == FP8_E5M2 else 0}")
    
    # STORAGE_TYPE typedef for FP8: set to uchar (OpenCL unsigned byte)
    # When STORAGE_TYPE_IS_FP8==1, kernel argument declarations use
    # __global uchar* and all access must go through load_storage/store_storage.
    # Direct arithmetic on STORAGE_TYPE is prohibited in FP8 mode — the
    # load/store macros handle FP8↔COMPUTE_TYPE conversion.
    if is_fp8:
        flags.append("-DSTORAGE_TYPE=uchar")
    
    # Compute type flags (required for FP8 load/store dispatch)
    # These may already exist for non-FP8 configs; ensure they're always emitted.
    flags.append(f"-DCOMPUTE_TYPE_IS_HALF={1 if precision.compute_dtype == np.float16 else 0}")
    flags.append(f"-DCOMPUTE_TYPE_IS_DOUBLE={1 if precision.compute_dtype == np.float64 else 0}")
    
    return flags
```

**Note:** The `COMPUTE_TYPE_IS_HALF` and `COMPUTE_TYPE_IS_DOUBLE` flags are used by the FP8 `load_storage_fp8()` / `store_storage_fp8()` functions (Step 9B.3) to dispatch to the appropriate return type (`half`, `float`, or `double`). These flags may already be emitted for FP16/FP64 compute configs; ensure they're present for FP8 configs as well.

## 4. Technical Notes

### FP8 conversion performance

The lookup table approach for FP8→FP32 is optimal (single memory access). FP32→FP8 conversion requires bit manipulation (~15-20 ALU operations per value). For bandwidth-bound workloads, the conversion overhead is amortized by the 4× reduction in memory bandwidth.

### Constant memory limits

OpenCL constant memory is typically 64KB per kernel. Each FP8 lookup table is 256×4=1KB. Two tables (E4M3, E5M2) require 2KB. This is well within limits.

### No native FP8 fast path

As of 2026, no OpenCL extension provides native FP8 types. The software emulation path is the only implementation. The `CL_FP8_NATIVE` codepath (ADR-025 §6.1) is a placeholder for potential future extensions.

### FP64 NaN-before-clamp ordering

The FP64 store path must check `isnan()` **before** the `fmin`/`fmax` clamp. IEEE 754 minNum/maxNum semantics define `fmin(NaN, x) == x` and `fmax(NaN, x) == x`, so a NaN input would be silently converted to `±FLT_MAX` by the clamp, then stored as a saturated value instead of zero. The NaN check is placed inside the `#if COMPUTE_TYPE_IS_DOUBLE` block before clamping; the non-FP64 path checks `isnan()` after the widening `(float)val` cast (which preserves NaN). The CPU backend (Phase 9C) avoids this issue because it uses `if (val > ...)` comparisons, which return false for NaN.

### Subnormal rounding accuracy

The rounding shift distances (bit 19/20 for round bit, bits 20/21 for mantissa extraction) use fixed positions that are correct for **both** normalized and subnormal cases. After subnormal denormalization (`mant32 = (mant32 | 0x800000) >> shift`), the significant bits are right-shifted into positions that align with the fixed extraction window at bits [22:20] (E4M3) or [22:21] (E5M2). The round bit at position 19 (E4M3) or 20 (E5M2) correctly captures the first truncated bit, and sticky bits below capture the remainder. The early underflow check (`fval < MIN_SUBNORMAL * 0.5f`) prevents the subnormal path from reaching shift values large enough to push significant bits entirely below the extraction window (E4M3: max reachable shift = 4, MSB at bit 19 = round bit position; E5M2: max reachable shift = 3, MSB at bit 20 = round bit position). The rounding is therefore exact round-to-nearest-even for all reachable subnormal values. The roundtrip tests (Step 9B.5) validate against `ml_dtypes` reference values and should produce exact agreement for all representable inputs.
