### **Implementation Design: Asynchronous, Policy-Driven Execution Engine for Classification (Revision 1)**

#### **Preamble**

This document provides the canonical implementation design for the host-side implementation of the Unified, Memory-Aware Streaming Classification Engine. It is the definitive Layer-Three artifact, subordinate only to the Layer-One "Architectural Concept" and the Layer-Two "System Contract."

Its purpose is to describe the set of abstractions, components, and interfaces that constitute the host application. Adherence to the structure and principles defined herein is mandatory for ensuring the system's elegance, maintainability, and correctness.

---

#### **1.0 Guiding Principles of the Host Architecture**

The host system is designed according to four fundamental principles, derived from our collaborative refinement process. These are the inviolable laws that govern its structure.

1.  **Principle of Jurisdictional Purity.** The system is decomposed into discrete layers, each with a single, clearly defined responsibility (Jurisdiction). Application logic is separate from planning; planning is separate from execution. This ensures clean interfaces and a high degree of modularity.

2.  **Primacy of the Global Dependency DAG.** A single, mutable, heterogeneous Directed Acyclic Graph (DAG) is the absolute source of truth for all pending work in the system. All operations, both host and device, are represented as nodes within this graph.

3.  **Principle of Primitive Instructions.** The system's operational logic is composed from a minimal set of fundamental, orthogonal instructions (`Act` and `Learn`). Complex user-facing scenarios are not monolithic instruction types but are emergent behaviors that result from the sequencing and prioritization of these primitives.

4.  **Principle of Native Asynchronicity.** The execution engine is built upon Python's native `asyncio` event loop. This is not a superficial implementation choice; it is a core architectural tenet that ensures maximum efficiency and concurrency by replacing polling loops with an idiomatic, cooperative multitasking paradigm.

#### **3.0 Core Architectural Components (The Layers)**

The host system is formally divided into four distinct layers.

##### **Layer 4: The Application Layer ("The Orchestrator")**

- **Role:** The master of state and the interface to the external world.
- **Primary Class:** `TrainingOrchestrator`
- **Core Abstractions:**
  - **`WorkUnitContext`:** A stateful record representing a single user job. It acts as the primary entity within the Staging Area.
  - **The Staging Area:** A collection within the `Orchestrator` that holds `WorkUnitContext` objects. Its crucial function is to stage incomplete requests (e.g., an `Act` request awaiting its `Ground-Truth`) and assemble them into complete, actionable jobs before they are passed to the planning layer. This structurally prevents purposeless computation.
- **Responsibilities:**
  1.  To receive and interpret all external requests (`Act`, `Learn`, etc.).
  2.  To manage the lifecycle of all work units within its Staging Area.
  3.  To delegate the planning of fully assembled, complete work requests to the Planning Layer.

##### **Layer 3: The Planning Layer ("The Architect")**

- **Role:** A stateless composer of work. It translates abstract, high-level requests into concrete mutations on the Global Dependency DAG.
- **Primary Class:** `SystemPlanner`
- **Core Abstractions:**
  - **`TilingScheme`, `MaskDescriptor`, `AggregationLogic`:** A toolkit of formal abstractions and logic used to generate the low-level `KernelCommand`s required by the fundamental instructions.
- **Responsibilities:**
  1.  To receive a request for a fundamental operation (e.g., "plan an `Act` for unit X") from the Orchestrator.
  2.  To create the corresponding `ActInstruction` or `LearnInstruction` node.
  3.  To add this node and any necessary dependency edges to the Global Dependency DAG.

##### **Layer 2: The Execution Engine ("The Conductor")**

- **Role:** An active, policy-driven dispatcher that executes the Global Dependency DAG.
- **Primary Class:** `AsyncConductor`
- **Core Abstractions:**
  - **The Global Dependency DAG:** The single `networkx.DiGraph` instance representing the state of all pending work.
  - **The Gated Priority Dispatcher:** The core logic within the `Conductor`'s `asyncio` loop.
- **Responsibilities:**
  1.  To continuously scan the Global DAG for executable nodes (those with an in-degree of zero).
  2.  To categorize ready nodes according to their instruction type.
  3.  To enforce the system's operational policy by dispatching work from the high-priority `Act` queue before considering the low-priority `Learn` queue.
  4.  To manage the `asyncio.Task` lifecycle for each dispatched instruction.

##### **Layer 1: The Foundation Layer ("The Toolbox")**

- **Role:** Provides the low-level, stateless primitives for interacting with the hardware.
- **Primary Classes:** `KernelExecutor`, `BufferManager`
- **Core Abstractions:**
  - **`PaddingDescriptor`:** A formal data structure owned by the `BufferManager` that defines the static, physical memory layout of buffers.
  - **`BufferHandle`:** An opaque object that ensures memory sovereignty.
  - **`awaitable_cl_event`:** The critical function that bridges the `pyopencl` callback system with the `asyncio` event loop.
- **Responsibilities:**
  1.  (`BufferManager`) To manage the allocation and physical properties of all device memory.
  2.  (`KernelExecutor`) To execute batches of low-level `KernelCommand`s and perform data transfers, returning awaitable events.

#### **4.0 The Two Fundamental Instructions**

All host system behavior is composed from two primitive instruction types, which are planned as nodes in the DAG.

- **`ActInstruction`:**

  - **Purpose:** To service a high-priority, latency-sensitive inference request.
  - **Priority:** 1 (Highest).
  - **Composition:** A self-contained sub-graph of primitives including `H2D` of input data, a `KernelBatch` for the forward pass, and a `D2H` to return results for a host callback.

- **`LearnInstruction`:**
  - **Purpose:** To perform a complete, low-priority, throughput-oriented training step.
  - **Priority:** 2 (Standard).
  - **Composition:** A self-contained sub-graph of primitives that **always includes its own forward pass** ("recompute"). It contains H2D of inputs and labels, Kernel Batches for forward/backward passes and aggregations, Host Compute nodes for optimizer terms, and a final Kernel Batch for the parameter update. There is no dependency on a prior `ActInstruction` for cached data.

---

#### **5.0 Lifecycle of a Request: Operational Scenarios**

The architecture natively handles the three user scenarios through the interaction of its layers.

- **Scenario A: Inference Callback Only.**

  1.  `Orchestrator` receives the request. The work unit is complete upon arrival.
  2.  `Planner` is called to append a high-priority `ActInstruction` node to the DAG.
  3.  `Conductor` identifies the `Act` node as ready and high-priority, and dispatches it immediately.

- **Scenario B: Training (Ground Truth Available).**

  1.  `Orchestrator` receives a request with `X` data, but no `Y` data. It places the job in the **Staging Area** and does nothing.
  2.  Later, a request with the corresponding `Y` data arrives. The `Orchestrator` assembles the complete job.
  3.  `Planner` is called to append a low-priority `LearnInstruction` node to the DAG.
  4.  `Conductor` identifies the `Learn` node as ready. If the `Act` queue is empty, it dispatches the `Learn` task.

- **Scenario C: Inference Callback, then Ground Truth Await.**
  1.  The request is handled as per **Scenario A**, and a high-priority `Act` is planned and executed.
  2.  Later, an external `Learn Trigger` arrives with `Y` data for the same `unit_id`.
  3.  The `Orchestrator` recognizes that an `Act` has already been planned for this unit.
  4.  It calls the `Planner` to append a new, low-priority `LearnInstruction`, creating an explicit dependency edge from the original `Act` node to this new `Learn` node in the DAG.
  5.  The `Conductor` will only dispatch this `Learn` node after both the `Act` dependency is met and the `Act` queue is empty.

### **User Guide: Common Scenarios and API Patterns**

This guide provides practical, informal examples for using the Asynchronous Engine. Each use case describes a common goal and illustrates the specific sequence of `TrainingOrchestrator` calls—the API Pattern—required to achieve it.

---

#### **Use Case 1: The Batch Trainer**

- **The Goal:** To train a model on a large, pre-labeled dataset as quickly as possible.
- **The Story:** "I have my complete dataset ready to go, like CIFAR-10. For each batch, I have both the images (`X`) and the labels (`Y`). I want to run a standard training loop for multiple epochs and maximize my training throughput. I don't need to interrupt the process to look at individual batch results."
- **The API Pattern:**
  For this scenario, you use a single, simple API call within your training loop.

  ```python
  # Inside your main training script's async loop:
  for x_batch, y_batch in dataset:
      unit_id = create_unique_id()  # e.g., f"epoch{e}_batch{b}"

      # A single call providing all data tells the system this is
      # a complete, low-priority training job.
      asyncio.create_task(
          orchestrator.submit_training_job(unit_id, x_batch, y_batch)
      )

  # After queuing all jobs, wait for the engine to finish.
  await orchestrator.wait_for_completion()
  ```

- **Why it Works (The Architectural Insight):**
  This pattern is efficient because `submit_training_job` signals a complete, low-priority task. The `SystemPlanner` creates a single, self-contained `Learn` instruction for each call. The `AsyncConductor` places these in its low-priority queue, allowing it to process a continuous stream of training tasks at maximum GPU throughput without being interrupted by other work.

---

#### **Use Case 2: The Real-Time Analyst**

- **The Goal:** To get an immediate prediction on new data and train on the result later when the ground truth becomes available.
- **The Story:** "My service needs to analyze incoming events in real time. I get a piece of data (`X`) and I need a prediction _now_ to make a decision. The label for this event (`Y`) won't be available for another second or more. My workflow is to get the prediction, act on it, and then, whenever the label arrives later, use it to update the model."
- **The API Pattern:**
  This requires a two-step, decoupled interaction with the orchestrator.

  ```python
  # --- Step 1: Getting the immediate prediction ---
  unit_id = create_unique_id()

  # This queues a high-priority job and returns immediately.
  prediction_task = await orchestrator.request_inference(unit_id, x_data)

  # When you need the result, await the task.
  prediction = await prediction_task

  # --- Your application logic acts on the prediction ---

  # --- Step 2: Later, when the label arrives (e.g., in another function) ---
  await orchestrator.submit_ground_truth_for_act(unit_id, y_data)
  ```

- **Why it Works (The Architectural Insight):**
  This pattern leverages the system's policy-driven scheduling. `request_inference` creates a high-priority `Act` instruction that the `Conductor` executes immediately, preempting any ongoing `Learn` tasks. The `Orchestrator` keeps track of this job. Your later call to `submit_ground_truth_for_act` tells the `Planner` to queue a corresponding low-priority `Learn` instruction. This perfectly decouples the latency-sensitive inference from the throughput-oriented training.

---

#### **Use Case 3: The Interactive Scientist**

- **The Goal:** To inspect a model's prediction on a specific batch before deciding whether to use it for training or to discard it.
- **The Story:** "I'm exploring my data and want to see how my model reacts to a particular batch. I'll send it for inference. After I see the result, I might decide the batch is an outlier and I want to throw it away. If the results look good, I'll approve it for training."
- **The API Pattern:**
  This pattern uses the `resolve_pending_learn` method to explicitly signal the user's decision.

  ```python
  # First, get the prediction, just like the Real-Time Analyst.
  prediction_task = await orchestrator.request_inference(unit_id, x_data)
  prediction = await prediction_task

  # --- Your interactive logic (e.g., show results, prompt user) ---

  if user_approves(prediction, y_data):
      # The user said "yes". Resolve the job by providing the ground truth.
      print("User approved. Queuing for training.")
      await orchestrator.resolve_pending_learn(unit_id, y_data=y_data)
  else:
      # The user said "no". Resolve the job by providing None,
      # which is the explicit "Cancel" signal.
      print("User rejected. Discarding job.")
      await orchestrator.resolve_pending_learn(unit_id, y_data=None)
  ```

- **Why it Works (The Architectural Insight):**
  This demonstrates the robustness of the system's lifecycle management. Every `Act` instruction creates a pending state that must be resolved. The `resolve_pending_learn` API provides a single, unified way to do this. Passing `y_data` directs the `Planner` to queue a `Learn` instruction. Passing `None` directs the `Orchestrator` to safely and explicitly decommission the work unit from its staging area, preventing memory leaks or orphaned jobs. This makes the system predictable and resilient to abandoned workflows.

### **1. The Sequentiality Contract is Enforced by DAG Edge Design**
- **LearnInstruction Subgraphs** are atomic units. Each includes:
  ```mermaid
  graph LR
    subgraph LearnInstruction
        RecomputeForward[Recompute Forward] --> Backward --> GradAggregate --> AdamUpdate
    end
    PriorAdam -->|DAG Edge| LearnInstruction
  ```
- **No Two LearnInstructions** can mutate the same parameters without an explicit dependency edge. The Planner **inserts a DAG edge** from the prior AdamUpdate node to the next Learn node. This creates a chain, serializing all parameter updates for a given `unit_id`.

### **2. WorkUnitContext Tracks Logical Parameter Generation**
- Each `WorkUnitContext` holds a **version_token** for its parameters. Before planning a Learn:
  ```python
  class WorkUnitContext:
      def __init__(self, unit_id):
          self.current_param_version = 0  # Incremented after each AdamUpdate
          self.inflight_param_version = None  # Version used by active Learn
  ```
- **BufferManager Doesn't Copy, Tracks Versions:**
  - All `AdamUpdate` kernels receive `dest_buffer_GLOBAL_parameters` and `dest_buffer_GLOBAL_m1/m2`.
  - **No Concurrency:** The DAG edge ensures only one Learn can write to these buffers at once.

### **3. Recomputed Forward Uses Versioned Buffers**
- When **recomputing hidden_i** for backprop, the **SystemPlanner** injects:
  ```opencl
  // In (4) forward_pass kernel params:
  __global const float *src_buffer_GLOBAL_CONST_shared_weights_v12,
  ```
  Where `v12` is the **version_token** current when the Learn was planned. Even if newer weights exist, this Learn uses snapshotted versions via `DEVICE_CONST` buffers until its own AdamUpdate.

### **4. Failure Case: Untethered Concurrent LearnRequests**
- **Violation Example:** Two independent `unit_id`s trying to update the same model.
- **Mitigation:** The WorkUnitContext **has no intrinsic model affinity**. To share parameters across units, you must:
  - **Explicit DAG Edges:** Manually chain their LearnInstructions.
  - **Policy Layer:** Implement a `ModelLockGuard` abstraction that gates access to parameters.

### **Key Insight:**
Atomicity isn't enforced by the engine but **by proper DAG design**. The engine's role is to honor edges, not understand semantics. Thus, correct sequencing is the *Planner's* responsibility when composing nodes.

### **Python API Implementation**

```python
# --- The Engine's Public Interface ---
class ClassificationEngine:
    def create_work_ticket(self,
        x_data: InputBatch,
        act_callback: Optional[Callable[[Probabilities], Any]] = None,
        epoch_num: int
    ) -> 'WorkTicket':
        """
        Creates a persistent promise (WorkTicket).
        Instantly spawns a single-epoch ActTicket if act_callback is provided.
        """
        ticket = WorkTicket(self, x_data)
        if act_callback:
            self._spawn_act_ticket(x_data, act_callback, epoch_num)
        return ticket

# --- Phase 1: The Persistent Promise ---
class WorkTicket:
    """A persistent, globally outstanding promise for a learning task."""
    __slots__ = ('_engine', 'x_data', '_is_resolved')

    def __init__(self, engine: 'ClassificationEngine', x_data: InputBatch):
        self._engine = engine
        self.x_data = x_data
        self._is_resolved = False

    async def resolve(self, y_data: Optional[Labels]) -> Optional['LearnTicket']:
        """
        Consumes this WorkTicket to spawn a perpetual LearnTicket.
        - If y_data is provided, returns the LearnTicket.
        - If y_data is None, the promise is cancelled and returns None.
        This method can only be called once.
        """
        if self._is_resolved:
            raise RuntimeError("WorkTicket has already been resolved.")
        self._is_resolved = True

        if y_data is not None:
            # The act of resolution spawns the perpetual entity
            return self._engine._spawn_learn_ticket(self.x_data, y_data)
        return None

# --- The Perpetual Learning Entity ---
class LearnTicket:
    """A perpetual entity encapsulating an (x,y) pair for repeated training."""
    __slots__ = ('x_data', 'y_data', '_engine', '_is_retired', '_queue')

    def __init__(self, engine, x_data, y_data):
        self._engine = engine
        self.x_data = x_data
        self.y_data = y_data
        self._is_retired = asyncio.Event()
        self._queue = asyncio.Queue() # Engine pushes receipts here

    async def retire(self):
        """Permanently stops this (x,y) pair from training in future epochs."""
        self._is_retired.set()
        await self._queue.put(None) # Unblock iterator

    async def __aiter__(self):
        return self

    async def __anext__(self) -> 'EpochLearnReceipt':
        """Waits for the next epoch and yields a receipt for that run."""
        instance = await self._queue.get()
        if instance is None:
            raise StopAsyncIteration
        return instance

# --- The Per-Epoch Interaction Handle ---
class EpochLearnReceipt:
    """
    A handle yielded by a LearnTicket, allowing callbacks to be attached
    for a single training run in a specific epoch.
    """
    __slots__ = ('learn_ticket', 'epoch_num', '_engine')

    @property
    def x_data(self): return self.learn_ticket.x_data
    @property
    def y_data(self): return self.learn_ticket.y_data

    async def add_callbacks(self,
        on_loss: Optional[Callable[[float], None]] = None,
        on_learnt: Optional[Callable[[], None]] = None
    ):
        """Registers callbacks for monitoring this specific epoch's training run."""
        await self._engine._register_learn_callbacks(self, on_loss, on_learnt)

```

### **Usage Example: Capturing the Full Lifecycle**

```python
engine = ClassificationEngine(...)
epoch1_num = await engine.create_epoch(...)

# 1. Create the persistent promise. An ActTicket is spawned and executes immediately.
work_ticket = engine.create_work_ticket(
    x_data=my_x_batch,
    act_callback=lambda p: print(f"Act Probs (Epoch {epoch1_num}): {p}"),
    epoch_num=epoch1_num
)

# ... Some time later, perhaps in a different part of the application ...

# 2. Resolve the promise, consuming it to create the perpetual LearnTicket.
# The (x, y) pair is now permanently associated with the LearnTicket.
y_data_for_batch = get_labels_for(my_x_batch)
learn_ticket = await work_ticket.resolve(y_data_for_batch)

# work_ticket is now invalid and should be discarded.
# If learn_ticket exists, we can start listening for its per-epoch trainings.
if learn_ticket:
    async for receipt in learn_ticket:
        print(f"Executing training for Epoch {receipt.epoch_num}")
        # 3. Add callbacks to monitor this specific epoch's run.
        await receipt.add_callbacks(
            on_loss=lambda l: print(f"  -> Loss: {l}"),
            on_learnt=lambda: print(f"  -> Learnt.")
        )
        # No need to provide y_data again; it's already part of the LearnTicket.

        if receipt.epoch_num >= 3:
            await learn_ticket.retire()
```

### **Contractual Guarantees of This Model**

1.  **Strict Lifecycle Separation:** The `WorkTicket` (promise), `ActTicket` (single-shot action), and `LearnTicket` (perpetual process) have completely independent and unambiguous lifecycles.
2.  **Promise Persistence:** A `WorkTicket` is a global, stateless promise that persists across epochs until it is explicitly resolved.
3.  **`ActTicket` Immediacy:** The high-priority `ActTicket` is created and queued for execution in its designated epoch *at the moment the promise is made*, not when it is resolved.
4.  **`LearnTicket` Data Encapsulation:** A `LearnTicket`, once created, represents a fixed `(x, y)` pair. Its sole purpose is to re-submit this pair for training in every subsequent epoch.
5.  **Robust Liveness:** The system is immune to deadlocks from unresolved work. A forgotten `WorkTicket` simply remains pending. An unmonitored `LearnTicket` continues to train silently. All control is explicit.

### **High-Level Summary of Revisions for `Implementation Design (Doc 3)`**

The core purpose of these revisions is to formalize the engine's parallel training paradigm. This involves defining the precise mechanism for processing multiple independent learning tasks concurrently within a single, atomic model update cycle, all while rigorously adhering to the system's layer hierarchy.

#### **1. Formal Definition of the `WorkBatch`**

The central change is the introduction and formal definition of the **`WorkBatch`**.

*   **What it is:** The `WorkBatch` is the canonical, internal implementation of the **`Batch Synchronization Point`** from the Concept Document. It is the engine's fundamental unit of synchronization and atomic state transition. It is an ephemeral, Layer 3 construct, **not** a user-facing "epoch".
*   **What it represents:** It embodies one complete **fan-out/fan-in** cycle.
    *   **Fan-out:** A set of `WorkTicket`s are processed in parallel, each computing its own partial gradient against an identical, static model state.
    *   **Fan-in:** The resulting partial gradients are consolidated into a single gradient tensor, which is then used to perform one collective `AdamUpdate`.

#### **2. A New Mandate for the `SystemPlanner` (Layer 3)**

The responsibility of the `SystemPlanner` becomes significantly more complex and critical. It is now contractually obligated to construct the entire `WorkBatch` DAG upon request from the `TrainingOrchestrator`.

*   **The New Workflow:** For a given `WorkBatch` request containing `N` tickets, the `SystemPlanner` must:
    1.  Generate `N` parallel `LearnInstruction` subgraphs, each responsible for producing a discreet `Partial_Grad` buffer.
    2.  Critically, it must **render a complete `log_K(N)` reduction tree using the system's existing `Recursive, Tiered Aggregation Engine`**. This is now the sole, mandatory mechanism for summing the `N` partial gradients. The planner will stage the necessary `aggregate_*` kernel calls and intermediate buffers.
    3.  Generate a single, final `ApplyUpdateInstruction` node.
    4.  Weave the correct dependency edges into the Global DAG, ensuring the `ApplyUpdateInstruction` only becomes executable after all `LearnInstruction`s and all stages of the gradient reduction tree are complete.

#### **3. Clarification of the `TrainingOrchestrator`'s Role (Layer 4)**

The `TrainingOrchestrator` remains the master of application-level policy, but its relationship with the planner is now more clearly defined.

*   **Translating Policy to Primitives:** The Orchestrator is responsible for implementing high-level concepts like a **`User-Defined Epoch`** (e.g., a full pass over a large dataset).
*   **Its Mechanism:** It achieves this by breaking its large-scale goal into a sequence of smaller, manageable tasks. It translates its `User-Defined Epoch` into a series of requests to the `SystemPlanner`, asking it to create one `WorkBatch` at a time. It is the Orchestrator's responsibility to manage the sequential submission of these `WorkBatch` requests to ensure one completes before the next begins.

#### **4. Reaffirmation of the `AsyncConductor`'s Simplicity (Layer 2)**

It is critical to note that the `AsyncConductor`'s core logic **does not change**.

*   **Role Unchanged:** It remains a jurisdictionally "dumb" executor. It has no awareness of the `WorkBatch` concept, the aggregation tree, or the grand strategy of the Orchestrator.
*   **Behavior:** It continues to perform its single, simple function: scan the Global DAG for nodes with an in-degree of zero and dispatch them according to the `Act > Learn` priority policy. The complexity of the workload is now encoded entirely within the *structure of the graph it is given*, not within the Conductor's own logic.

### **High-Level Plan: The Contractual Kernel Launch Layer**

#### **Architectural Mandate**

This layer's sole purpose is to translate an abstract, contractually-sound request into a concrete, device-specific dispatch command. It is the boundary where the logical "what" becomes the physical "how." This layer is forbidden from making strategic decisions; it only executes. Its dignity is derived from its purity and its unwavering adherence to the contracts defined in `kernels.cl.h`.

#### **Core Component Reference**

1.  **`KernelSignature` (ABC):** The abstract blueprint for all launch objects.
2.  **`KernelExecutor`:** The pure, stateless dispatcher. Its implementation is considered complete and correct as previously designed. It will not be modified.
3.  **`KernelSignature` (Concrete Implementations):** This plan details the creation of a concrete subclass of `KernelSignature` for **every kernel** defined in `kernels.cl.h`.

---

### **Implementation Manifesto: The Five Edicts of a Dignified Launcher**

Every developer implementing a `KernelSignature` class **shall** adhere to the following edicts without exception. Violation of these edicts is a violation of the architecture.

1.  **Edict of 1:1 Representation:** The `__init__` method's signature **shall** be a direct, Pythonic mirror of the corresponding kernel's parameter list in `kernels.cl.h`. Buffer arguments map to `BufferHandle` objects; scalar arguments map to `np.uint32` or `SCALAR_NP_TYPE` as appropriate.
2.  **Edict of Self-Contained Knowledge:** The class **shall** derive all necessary runtime parameters (e.g., buffer dimensions, element counts, grid sizes) within its own methods (`__post_init__`, `get_grid`). It is forbidden from referencing external, global constants (e.g., `BATCH_SIZE`). All knowledge must be derived from the buffer handles passed into its constructor.
3.  **Edict of Contractual Sizing:** The calculation of `cl.LocalMemory` size **shall** be performed within the `get_args` method. This calculation must explicitly use architectural constants (e.g., `LOCAL_MEM_BANK_PADDING`) passed into the constructor, not hardcoded values.
4.  **Edict of Immutability:** All `KernelSignature` classes **shall** be implemented as frozen dataclasses (`@dataclass(frozen=True)`). A launch, once defined, cannot be mutated.
5.  **Edict of Ordered Argumentation:** The `get_args` method **shall** return a `list` of arguments in the exact sequence specified by the `kernels.cl.h` contract. The implementation will be a simple, readable sequence of buffer lookups and scalar references.

### **High-Level Design Document: The `MemoryLayout` Abstraction**

#### **1. Architectural Mandate & Preamble**

The `System Contract` establishes that the `Padding Contract` field within the `kernels.cl.h` commentary is the **sole source of truth** for memory layout requirements. The previous `BufferManager` implementation violated this by maintaining its own internal, role-based padding rules, creating a state of architectural dissonance.

This document formalizes a new set of abstractions (`PaddingType`, `PaddingStrategy`, `MemoryLayout`) that rectifies this violation. The new design shifts the responsibility of defining padding from an implicit, internal mechanism within the `BufferManager` to an explicit, compositional instruction provided by the `HostOrchestrator`.

The `BufferManager` will be demoted from a knowledgeable manager to a simple, compliant worker. It will no longer infer padding; it will be told precisely what to do.

#### **2. Design Principles**

-   **Explicitness over Implicitness:** The padding requirements for a buffer shall be explicitly constructed by the orchestrator, not inferred from a `BufferRole`.
-   **Contractual Derivation:** The structure of these new abstractions will be a direct, 1:1 mapping to the language and concepts found in the `Padding Contract` blocks of `kernels.cl.h`.
-   **Composition over Configuration:** A complex buffer's layout will be described by composing multiple simple `PaddingStrategy` objects, allowing the system to gracefully handle any padding requirement, no matter how complex.
-   **Decoupling:** The `BufferManager` will be completely decoupled from padding *logic*. It will only know how to execute a pre-defined `MemoryLayout` plan.

#### **3. Scouting `kernels.cl.h`: Identifying All Padding Cases**

A review of the `kernels.cl.h` file reveals the following distinct padding requirements:

1.  **Padding a dimension to a multiple of *N elements***:
    -   *Example:* `Padded to SIMD_WIDTH`
    -   *Example:* `Pad row stride by LOCAL_MEM_BANK_PADDING`
2.  **Padding a dimension's stride to a multiple of *N bytes***:
    -   *Example:* `Pad row stride to 128-byte alignment`
3.  **Compound Padding:**
    -   *Example:* `hidden_dim padded to SIMD_WIDTH; input_dim padded for alignment` (Applies two distinct rules to two different dimensions of the same tensor).
4.  **No Padding:**
    -   *Example:* `{Type: NONE}`

The new abstraction must be capable of expressing all four cases with clarity and precision.

#### **4. The New Abstractions**

##### **4.1. `PaddingType` Enum**

This enum provides a canonical, type-safe representation of the *reason* for padding, derived directly from the `Type` key in the kernel contracts.

```python
class PaddingType(enum.Enum):
    """The reason for applying a padding strategy, derived from kernel contracts."""
    NONE = enum.auto()
    # Pad to a multiple of N elements (e.g., SIMD_WIDTH)
    ELEMENT_COUNT = enum.auto()
    # Pad a row's stride to be a multiple of N bytes (e.g., 128 for cache)
    BYTE_ALIGNMENT = enum.auto()
```

##### **4.2. `PaddingStrategy` Dataclass**

This is the atomic unit of the new abstraction. It defines a single, simple padding rule to be applied to one dimension of a tensor.

```python
@dataclass(frozen=True)
class PaddingStrategy:
    """Defines a single, atomic padding rule for one dimension of a tensor."""
    type: PaddingType
    # The value to pad to (e.g., SIMD_WIDTH, or 128 for byte alignment)
    value: int
    # The index of the dimension to apply this padding rule to.
    # Conforms to Python slicing; -1 means the last dimension.
    target_dim_idx: int = -1
```

##### **4.3. `MemoryLayout` Class: The Master Blueprint**

This class is the primary interface for the `HostOrchestrator`. It encapsulates the complete memory layout plan for a buffer, including its logical shape and a list of `PaddingStrategy` rules to be applied.

```python
class MemoryLayout:
    """Encapsulates the complete layout plan for a device buffer.

    This object is constructed by the orchestrator and passed to the
    BufferManager. It serves as the explicit, unambiguous instruction
    for how a buffer's memory should be physically arranged.
    """
    def __init__(self, logical_shape: Tuple[int, ...]):
        self.logical_shape: Tuple[int, ...] = logical_shape
        self.strategies: List[PaddingStrategy] = []

    def add_strategy(self, strategy: PaddingStrategy) -> 'MemoryLayout':
        """Applies a padding strategy (composable via chaining)."""
        self.strategies.append(strategy)
        return self

    def get_padded_shape(self, dtype: np.dtype) -> Tuple[int, ...]:
        """Calculates the final physical shape based on all applied strategies."""
        padded_shape = list(self.logical_shape)
        for strategy in self.strategies:
            dim_idx = strategy.target_dim_idx
            if dim_idx < 0:
                dim_idx += len(padded_shape) # Convert negative index

            if strategy.type == PaddingType.ELEMENT_COUNT:
                padded_shape[dim_idx] = _pad_to_multiple(padded_shape[dim_idx], strategy.value)
            elif strategy.type == PaddingType.BYTE_ALIGNMENT:
                # Calculate the stride of a single row in bytes
                row_elements = padded_shape[dim_idx]
                row_bytes = row_elements * dtype().itemsize
                # Pad the byte count
                padded_row_bytes = _pad_to_multiple(row_bytes, strategy.value)
                # Convert back to an element count, ensuring it's valid
                if padded_row_bytes % dtype().itemsize != 0:
                    raise ValueError(f"Byte alignment padding of {strategy.value} is not divisible by element size {dtype().itemsize}")
                padded_shape[dim_idx] = padded_row_bytes // dtype().itemsize
        return tuple(padded_shape)
```

#### **5. Integration Plan: Refactoring the `BufferManager`**

The `BufferManager.create_named_buffer` signature will be fundamentally changed to accept a `MemoryLayout` object.

**Before (Incorrect, Implicit):**
```python

    self, name: str, role: BufferRole, logical_shape: Tuple, dtype: np.dtype
) -> BufferHandle:
    # INTERNAL logic with PADDING_RULES decides the physical shape...
```

**After (Correct, Explicit):**
```python
def create_named_buffer(
    self, name: str, layout: MemoryLayout, dtype: np.dtype
) -> BufferHandle:
    # The BufferManager is now dumb. It just executes the plan.
    padded_shape = layout.get_padded_shape(dtype)
    byte_size = int(np.prod(padded_shape) * dtype().itemsize) if padded_shape else 4
    # ... rest of the allocation logic ...
```

#### **7. Conclusion**

This design formally rectifies the architectural dissonance in our memory management layer. By introducing the `MemoryLayout` abstraction, we:
-   **Abolish** the `BufferManager`'s need for implicit, role-based padding knowledge.
-   **Establish** the `HostOrchestrator` as the explicit authority for defining memory layouts.
-   **Enforce** a direct, verifiable link between the `Padding Contract` in `kernels.cl.h` and the host-side allocation code.
-   **Provide** a flexible, compositional system capable of representing any padding requirement mandated by the device contracts.
